# Codex 单人生产级开发方式

> 临港住房项目执行手册 · v1.1 · 2026-07-22  
> 目标：一个人使用 Codex，也能稳定交付符合需求、设计和生产标准的软件，而不是只做出能运行的 Demo。

## 一、先说结论

你原来的方式——先整理需求和原型，再写实施计划，最后让 Codex 分批开发测试——方向没有错。真正的问题是：

1. 需求、原型、接口和计划分散在多份不同时间的文档里，没有一份“当前有效口径”。
2. 任务主要按数据库、后端、前端等技术层拆分，没有按完整用户流程交付。
3. 原计划明确允许“不和原型一比一还原”，而你的真实期望其实是高度还原。
4. 测试主要证明功能和构建通过，真实运行截图和视觉比较进入得太晚。
5. “开发完成、功能通过、视觉通过、可以上线”被混成了同一个“完成”。

项目证据也印证了这一点：功能 UAT 已达到 25/25 页面、0 运行时异常，但当时全局视觉审计只有 69/90；后续还专门增加 D+ 阶段重新按原型逐页整改。

所以，新的开发方式不是增加更多文档，而是建立一条短、硬、可验证的交付链：

```text
当前口径 → 用户流程 → 页面/接口契约 → 小任务 → 实现 → 自动化验证 → 真实运行验收 → 发布观察
```

生产级的判断公式是：

```text
生产就绪 = 业务正确 × 设计忠实 × 工程可靠 × 安全合规 × 可运维 × 可回滚
```

任何一项没有证据，都不能称为生产就绪。

## 二、只保留一套工作方式

### 1. 探索和交付必须分开

想法还不清楚时，进入探索模式：可以讨论、画原型、写临时代码，但不宣布完成，也不直接作为生产代码。

目标、流程和设计确定后，进入交付模式：需求和原型成为合同，任何范围变化都必须先更新任务，而不是让 Codex 边写边猜。

### 2. 每次只交付一个完整用户目标

不要再采用：

```text
先做所有表 → 再做所有后端 → 再做所有前端 → 最后统一还原页面
```

改成垂直切片：

```text
一个用户目标
→ 固定测试数据
→ 页面与状态
→ 最小接口、权限和数据变更
→ 前后端实现
→ 自动化测试
→ 真实运行截图和流程验收
```

例如“员工完成报修”是一个任务域；“把所有工单表和接口先写完”不是一个能被用户验收的交付结果。

## 三、标准开发流程

### 第 1 步：确认当前有效口径

开工前只回答六个问题：

- 本轮解决哪个用户问题？
- 哪份需求和哪张原型是当前版本？
- 哪些旧文档只作为历史参考？
- 本轮明确不做什么？
- 验收人如何判断结果正确？
- 当前有哪些外部阻断？

不要把所有历史文档一次性提供给 Codex。默认只提供当前任务需要的 3～5 个一手来源，并精确到章节、页面或图片。

首次接管老项目或进入大版本改造前，只做一次基线确认：当前可构建状态、公开行为、接口/权限/数据边界、测试与历史失败、安全配置、部署方式、已知风险和债务。基线只描述事实，不顺手修复；未确认的历史失败不能被新变更掩盖，新变更也不得扩大失败范围。后续任务引用这份既有基线，不重复制造基线文档。

### 第 2 步：冻结页面和业务契约

涉及页面时，编码前必须明确：

- 原型文件和版本；
- 页面路由、角色和入口；
- 正常、加载、空、错误、无权限和极端数据状态；
- 点击、返回、滚动、弹层、键盘和失败重试行为；
- 接口、字段、权限和固定测试数据；
- 目标设备、视口、设计 Token 和关键尺寸；
- 业务规则覆盖原型的地方及原因；
- 真实运行验收方式和目标截图。

这一步解决“功能做对了，但页面和我想的不一样”。

### 第 3 步：建立单张任务卡

每轮 Codex 开发只使用一张任务卡，模板见本文末尾。任务必须满足：

- 只有一个可观察目标；
- 明确允许和禁止修改的范围；
- 验收标准可验证；
- 验证命令可直接执行；
- 有停止条件和回滚点。

任务卡从“讨论稿”进入“允许实施”时，必须记录 `TASK-ID`、批准时间和内容摘要。摘要覆盖当前需求、原型版本、允许范围、验收标准、计划和测试计划；其中任一项变化，批准及已有验证证据自动失效，必须重新确认。初期人工记录摘要，流程稳定后由脚本计算 SHA-256，禁止为每次变更新建一套规格目录。

出现以下情况，Codex 必须停止实现并重新规划：

- 需要修改禁止范围；
- 发现未定义的业务规则或页面状态；
- 需要增加新依赖、大型兼容层或跨域重构；
- 连续两次对同一要求理解不同；
- 补丁已经无法在一次审查中解释清楚。

### 第 4 步：先验证预期，再写最小实现

执行顺序固定为：

```text
只读定位
→ 列出冲突和假设
→ 写失败测试或验收用例
→ 最小实现
→ 局部验证
→ 全量适用门禁
→ 真实运行验收
→ 独立审查
```

禁止顺手重构、无依据扩展需求、用占位数据伪装业务完成，或者为了让测试变绿而降低验收标准。

对可自动测试的行为，RED 不是“写了一个测试”，而是必须真实运行并保存：验收 ID、测试命令、退出码、预期失败原因、基线 Git SHA、测试与相关代码摘要和时间。导入错误、环境错误、测试自身错误及无关历史失败不算 RED。随后只写使该行为通过的最小实现，取得 GREEN 后才允许重构，并重新运行受影响测试。已有覆盖率门禁时不得下降，但覆盖率数字不能替代行为断言。视觉和真机行为无法完全单测时，先建立会失败的 Playwright、契约或人工验收用例，并把临时人工证据标为限期自动化债务。

### 第 5 步：分维度验收

不要再填写一个笼统的“完成”。每次交付分别给出：

| 维度 | 允许结论 | 核心证据 |
|---|---|---|
| 功能 | Pass / Fail / Blocked / N/A | 验收用例、单测、E2E |
| 设计 | Pass / Fail / Blocked / N/A | 真实运行截图、视觉差异、可访问性 |
| 集成 | Pass / Fail / Blocked / N/A | API、数据库、权限、第三方测试 |
| 安全与隐私 | Pass / Fail / Blocked / N/A | 越权、敏感数据、秘密和依赖检查 |
| 数据迁移 | Pass / Fail / Blocked / N/A | 克隆库演练、备份和恢复 |
| 发布运维 | Pass / Fail / Blocked / N/A | 制品、配置、监控、回滚和观察 |

`Blocked` 和 `N/A` 不能留空，必须说明原因。代码、依赖、配置或迁移变化后，旧证据自动失效。

每个 `REQ / UX / API / DATA / SEC / OPS` 验收 ID 必须追溯到实现文件、自动化测试、运行截图或日志、Git 提交和当前结论。初期可由任务卡维护；流程稳定后由 CI 自动生成追踪矩阵。缺少追踪证据的验收项不能标记为 Pass。

### 第 6 步：真实运行验收

- 管理后台和 H5：核心流程必须进入 Playwright E2E 和 `toHaveScreenshot()` 视觉基线；自动化尚未落地的流程只能使用人工截图作为临时证据，并记录为发布阻断或限期风险。
- 微信小程序固定执行：源码门禁 → 正式构建 → 微信开发者工具自动化与全路由冒烟 → 真实 AppID/HTTPS 环境 → 真机核心流程、授权、性能和截图。任一步失败都不能用 H5 结果代替。
- 视觉基线只能由人确认。禁止为了消除失败自动接受所有新截图。
- 像素差异只是报警器；信息架构、品牌层级、交互位置和业务语义仍需人工判断。

### 第 7 步：冻结证据再发布

测试、UAT 和发布必须指向同一个 Git SHA 和同一构建制品。发布记录至少包含：

- Git SHA、工作树状态和 CI Run；
- 依赖锁、配置版本和制品摘要；
- 迁移集合、备份、恢复和回滚结果；
- 监控、告警、核心流程和回滚触发条件；
- 未关闭风险及负责人。

当前项目的 `yijia_001` 会删除并重建奕家业务表，只能用于确认过的空库，禁止在生产存量库执行。增量迁移应先在存量克隆库演练，并优先准备前向修复。

生产发布还必须满足：

- 新功能和高风险变更通过服务端功能开关控制，默认关闭，记录负责人、启用范围、到期清理日期和一键关闭方式；
- 按内部账号 → 小流量/单服务中心 → 扩大范围 → 全量的顺序灰度，提前定义每阶段观察时间、成功阈值和自动/人工回滚阈值；
- 为可用性、错误率、延迟和核心业务成功率定义 SLI/SLO；告警必须有值班负责人、升级路径和处置手册，不能只发送无人负责的通知；
- 建立 P0～P3 事故分级、响应负责人、止损/回滚、内部外部沟通和恢复后复盘流程；复盘结论必须变成测试、监控、规则或任务；
- 发布后在观察窗口检查技术指标、真实用户反馈和业务指标，未达到阈值时停止放量或回滚。

## 四、Codex 使用规则

### 1. `AGENTS.md` 只放稳定规则

保留构建测试命令、代码约定、业务边界、安全禁令和权威资料入口。不要把需求全文、历史讨论和当前任务进度持续堆进去。能通过测试、Lint 或脚本强制的规则，不要只靠提示词。

### 2. 一个 Codex 任务只处理一个垂直切片

切换业务域、上下文被反复修正、目标发生变化时，开启新任务，并把当前状态写回任务卡。对话记忆不能作为事实源。

### 3. 要求 Codex 先读、再说、再改

推荐开场指令：

```text
先不要修改代码。读取任务卡和列出的当前有效资料，定位相关代码、接口、权限、SQL 和测试。
先报告事实、冲突、假设、影响文件、最小实施计划和验证方式。
确认信息足够后按任务卡最小实现；发现超范围或新业务歧义时停止实现并报告。
完成后必须提供实际执行的命令、结果、运行证据、未验证项和剩余风险，不得用“应该可以”代替证据。
```

### 4. 子代理只做独立且边界清楚的工作

适合：代码定位、测试审查、安全审查、文档核对。共享核心文件、强顺序依赖和小任务不要拆代理。主代理始终负责统一口径和最终验证。

### 5. 单人开发也要分离决策职责

同一个人可以承担多种角色，但必须分时、分证据审查，不能让“刚写完代码的自己”一次性代表所有角色：

| 角色 | 必须确认的事项 |
|---|---|
| 产品 | 用户目标、范围、业务规则和成功指标 |
| 设计 | 页面状态、交互、视觉基线和可访问性 |
| 开发 | 架构、实现、测试、迁移和可维护性 |
| 测试 | 从需求独立推导用例，复核 AI 测试没有复制实现错误 |
| 安全/隐私/法务 | 权限、敏感数据、供应链、协议和合规适用性 |
| 发布/运维 | 制品、配置、灰度、SLO、告警、值班和回滚 |

L1 变更至少进行一次脱离实现上下文的独立审查；L2 及生产发布必须由第二位人类或具备职责的专业方复核。AI 子代理只能提供额外检查，不能冒充多人审批。

### 6. 渐进式披露和跨任务恢复

新任务启动时先读取本手册、当前任务卡及其直接依据，不把全部历史文档重新塞入上下文。`AGENTS.md` 只提供稳定规则和权威入口；任务进度不能只存在于聊天记忆。

流程稳定后允许增加一个机器维护的状态文件，但它只能是缓存和门禁输入，不能成为第二份人工规格。最小字段为：`taskId`、风险级别、当前阶段、批准摘要、基线 Git SHA、验证指纹、阻断项、下一动作和最后更新时间。`status` 命令必须能从任务卡、Git 和验证结果重建状态；状态文件损坏时不得丢失事实源。禁止生成 `spec/baseline/features/changes/archive` 等大批人工文档来复制同一事实。

### 7. Git 动作分级授权

本地原子提交只有在当前任务授权且门禁通过后才能创建。`push`、创建或合并 MR/PR、打 tag、发布、删除分支和强制推送属于不同外部动作，必须分别获得明确授权。禁止为了获得干净工作树擅自 stash、reset、覆盖或删除用户改动；发现无关脏文件时隔离范围并如实记录。

## 五、质量、安全和发布底线

当前项目优先复用已有统一检查入口：

```bash
cd lc-govkit
node scripts/govkit-check.mjs --group static
node scripts/govkit-check.mjs --group build
node scripts/govkit-check.mjs --group test
node scripts/govkit-check.mjs --group runtime
node scripts/govkit-check.mjs --group all
```

根据风险选择适用组；发布候选运行 `all` 并阅读完整输出。若环境阻断，记录为 `Blocked`，不能当作通过。

重复执行两轮后，将以下状态机固化进项目级门禁脚本；在自动化完成前，任务卡按同一口径人工记录：

```text
baseline → drafting → approved → red → implementing → green → refactoring → verifying
→ runtime-acceptance → reviewing → ready-to-release → observing → closed
```

门禁至少包括：

- `check start`：任务卡已批准、批准摘要有效、分支和工作树状态明确；
- `check implement`：L1/L2/Emergency 已取得有效 RED 或故障复现证据，未进入禁止范围；
- `check commit`：暂存文件属于允许范围，依赖、迁移和敏感变更已批准，验证指纹与当前内容一致；
- `check push`：提交历史、任务结论、剩余风险和远端目标明确；
- `check release`：CI、真实运行、独立审查、迁移、制品、监控和回滚证据均指向同一 Git SHA 与制品摘要。

另提供只读 `status` 和 `doctor`：前者展示当前事实、阻断和下一动作，后者检查工具链、配置、状态一致性和门禁可用性；二者不得自动修复或改写业务事实。

验证指纹至少覆盖 `TASK-ID + 批准摘要 + Git SHA/工作树内容摘要 + 实际测试命令及退出码 + 制品摘要`。验证后代码、测试、依赖、配置、迁移或批准内容发生变化，旧指纹立即失效。任何脚本都不能只检查“已勾选”文本来冒充真实 RED、独立审查或发布批准。

CI 必须成为合并和发布的强制门禁，至少自动执行：静态检查、类型检查、单元/集成/E2E、权限与接口契约、秘密扫描、依赖漏洞、SBOM/许可证、数据库迁移演练、生产构建和制品摘要校验。失败默认阻断；人工绕过必须有书面风险接受、负责人、期限和补偿措施。测试、UAT 和部署必须引用同一 Git SHA 与制品摘要。

安全底线包括：

- 登录、会话、租户、角色、数据范围和越权；
- 身份证号、手机号、门锁密码、账单和附件的最小化、脱敏与留存；
- 密钥、AppID、证书、域名和默认口令不得进入代码或文档；
- SQL、上传、导出、日志、依赖、SBOM 和许可证；
- 微信隐私授权、第三方数据共享和协议法务审定；
- 备份恢复和迁移回滚必须真实演练。

Codex 可以整理安全与合规证据，不能替代最终的安全、法务和生产发布判断。权限、敏感数据、生产迁移、支付、门锁和外部厂商等高风险变更，需要第二位人类或专业方复核。

## 六、风险分级，避免流程过重

| 级别 | 典型变更 | 最低要求 |
|---|---|---|
| L0 | 文档、无行为文案、纯样式微调 | 范围、静态检查、目标截图或文档审查 |
| L1 | 普通功能和用户流程 | 任务卡、自动化测试、运行验收、独立审查 |
| L2 | 权限、敏感数据、迁移、支付、外部集成、架构 | 全量门禁、备份回滚、第二人复核、发布观察 |
| Emergency | 生产故障最小热修 | 复现、最小补丁、关键回归、回滚和监控；事后补齐证据与复盘 |

不确定时按更高一级处理。它们分别承担轻量、完整和热修通道，不再另建 `light/full/hotfix` 第二套分类。范围扩大时立即升级，降级必须说明依据。流程服务于风险，不是为了制造文档。

## 七、唯一任务卡模板

每次开发把下面内容复制到 Codex 任务中，不再额外创建一套文档体系：

~~~~markdown
# 任务：一句话说明用户结果

TASK-ID：
状态：drafting / approved / red / implementing / green / refactoring / verifying / runtime-acceptance / reviewing / ready-to-release / observing / closed
风险级别：L0 / L1 / L2 / Emergency
批准时间与内容摘要：

## 当前有效依据
- 需求章节：
- 原型/设计稿：
- 相关接口/数据/权限：

## 允许范围
- 可修改：
- 可新增：

## 禁止和非目标
- 禁止修改：
- 本轮不做：

## 验收标准
- REQ-001：
- UX-001：
~~~~

## 八、当前项目从明天开始这样执行

1. 先确定当前最重要的一条用户流程，不再继续扩大全局计划。
2. 用本文任务卡把需求、原型、状态、接口和验收压缩成一个上下文包。
3. Codex 先只读核对，再按垂直切片开发。
4. 自动化测试和真实运行截图同时作为完成条件。
5. 每轮记录返工原因：需求不清、设计变化、上下文错误、实现错误或环境问题。
6. 连续完成两个切片后再复盘流程；只有重复且稳定的步骤才做成 Skill、Hook 或 CI 自动化。
7. 优先固化批准摘要、RED 证据、验证指纹和 `start/implement/commit/push/release` 门禁；机器状态只保存索引，不复制需求正文。

衡量是否变快，不看代码行数、Token 或对话轮数，只看：首次验收通过率、视觉首次通过率、返工时间、逃逸缺陷、交付周期和发布失败率。

每个上线切片还必须定义业务成功指标和用户反馈入口。例如入住完成率/耗时、报修响应与解决时长、账单支付成功率、用户投诉与满意度。发布前记录基线和目标，发布后按观察窗口复核；技术指标正常但用户或业务指标恶化，同样视为发布失败。连续两个切片后用数据决定保留、删除或调整流程步骤。

## 九、工具选择原则

- 现在：Git、现有测试脚本、真实运行环境和本手册已经足够。
- Wu5 Dev Flow 只借鉴批准哈希、状态恢复、验证指纹、风险通道和 Git 门禁；不直接安装或复制其 Python/pytest/pyright、GitHub/Squash、拒绝数据库迁移及多层 `spec/` 文档结构。项目级实现必须适配 Java、Vue、UniApp、GitLab CI、Playwright、微信真机和存量数据库迁移。
- Figma 成为权威设计源后，再接入 Figma MCP；当前本地 PNG 不需要制造第二事实源。
- 项目迁移到 GitHub 并使用 Issue/PR/Checks 后，再接入 GitHub 插件；当前已有 GitLab CI。
- Notion、Drive、Slack 等只有成为唯一权威源时才接入，单人开发不要复制状态。
- 流程连续稳定运行两次后，再把重复动作固化成 Skill 或 Hook。
