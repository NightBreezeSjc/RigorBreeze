## 1. 运行原则

### 交付一个可观察结果

按照完整用户路径拆分任务：

```text
用户结果
→ 最小接口、数据和页面变更
→ 自动化行为证明
→ 真实运行验收
```

不要把一个功能拆成“先完成所有数据库，再完成所有接口，最后完成所有页面”。每个任务必须产生用户或独立预期可以观察到的结果。

### 把一份任务作为当前合同

每个变更只有一份人工 Markdown 合同，其中包含：

- 权威需求或设计来源；
- 允许、禁止和非目标范围；
- 可观察验收 ID；
- 公共测试接缝和独立预期结果；
- 项目实际验证命令；
- 仅在适用时填写的 UI、安全、迁移或发布控制。

`Runtime-Claims` 只声明任务实际使用的独占资源：`port`、`service`、`process`、`app` 或 `environment`；其余情况使用 `none`。worktree 只能隔离文件，无法隔离这些资源，因此活动声明冲突会阻断批准和窗口认领。RigorBreeze 只报告冲突，不杀进程、不关闭工具、不抢占端口。

对于条件化 L2 外部集成，`Operational-Modes` 将 `enabled`、`disabled`、`unavailable` 映射到合同中已声明的验收 ID。每个模式必须通过当前 RED/GREEN 或绑定该需求的真实运行证据闭合。没有条件化运行行为时填写 `N/A - <原因>`。

Allowed Scope 只能填写仓库相对路径、目录前缀或 glob；`*` 只匹配一层路径，`**` 才跨目录，包含空格的合法路径仍可使用。验收条件必须包含唯一且机器可读的 ID。批准操作会冻结任务摘要，不能在生产实现变化之上重新批准。应恢复已批准合同并完成，或先回退生产变化，再修正并重新批准同一可观察结果；新增用户结果或验收条件才建立依赖切片。Git SHA、制品摘要、报告和完成结果属于机器证据，不要求开发者在实现前预测填写。

### 不让用户操作内部机械流程

Codex 负责执行 `new`、批准、RED、验证、证据、门禁和归档命令。开发者通常只需要：

1. 批准目标、范围和验收边界；
2. 在真实产品环境中验收结果；
3. 为非 L0 工作确认预填复盘。

Git 和发布自动化保持 `manual`，除非项目显式选择更高的长期等级。`manual` 不授予无人值守权限，但用户当前消息的明确要求可以授权一次受保护的 commit 或 push。升级 Skill 永远不会提高权限。

## 2. 风险通道

| 通道 | 示例 | 最低关闭门禁 |
|---|---|---|
| L0 | 文档、无行为文案、孤立样式 | 配置的 affected 验证 |
| L1 | 功能、缺陷修复、端到端用户流程 | RED、full、真实验收、两轮审查、复盘 |
| L2 | 权限、敏感数据、迁移、支付、外部集成、架构、生产发布 | L1 加适用的安全、迁移、制品和发布控制 |
| Emergency | 最小安全生产修复 | 复现、关键回归、回滚、监控、事后证据修复 |

不要为了绕过门禁降低风险等级。范围或后果扩大时应升级。只有项目策略或真实重要决策要求时才强制第二位人类；AI 审查者不能冒充人工批准。

## 3. 执行一个垂直切片

### 在首个任务前塑形项目

只有当需求属于新产品、新业务域、大范围旧系统迁移，或者同时包含多个
尚无法批准为一个垂直切片的结果时，才进行一次精简塑形。边界已经稳定的
普通功能或缺陷直接跳过。

询问开发者前先读取项目与参考证据。优先复用已有且有版本的产品/设计来源；
如果没有，则在最小 Spec Tree 之外维护一个精简的项目塑形简报，只包含：

- 问题、目标用户、关键旅程、期望结果和成功指标；
- 已确认事实、假设、未知项及其来源；
- 两到三个可行方案、推荐结论和取舍；
- 价值、可用性、技术可行性和商业可持续性风险；
- 投入边界、风险坑、明确不做，以及最小且有用的首个切片。

只询问证据无法回答且会改变结果的少量问题。体验不确定时验证粗粒度流程或
原型；价值或运营规则不确定时，应取得真实用户、运营人员、合同、分析数据或
业务证据。参考源码只能证明旧系统曾经如何运行，不能证明新产品应该怎么做；
角色提示可以挑战方案，但不能补造意图或代替批准。

开发者批准简报后才创建任务，并在首个 RigorBreeze 合同中引用准确版本，随后
回到普通垂直切片流程。不要把路线图直接变成任务 DAG，不要把全部开放问题复制
进每个任务，也不要在最小 Spec Tree 旁再建立 proposal/design/task 文档树。后续
发现只更新权威产品来源以及真正受影响的未来任务。

### 定义任务

修改行为前读取当前需求、设计、代码、接口、权限、数据和测试。提出最小可观察任务。遇到未解决业务歧义、未批准依赖、意外迁移风险或范围扩张时停止实现。

不要求用户先写出完美提示词。Codex 应在现有 Authoritative inputs 中建立精简上下文：

- 从权威文档、当前行为、代码、测试、Git 和运行证据恢复项目事实；
- 沿受影响用户流程追踪业务规则、接口、数据、权限和失败边界，不必每次重读整个仓库；
- 记录用户结果、当前行为证据、架构路径、不变量/事实源、新鲜度与兜底语义，以及当前需求/设计/API 版本；
- 只询问证据无法确定且会改变结果的意图，安全默认值必须显式说明。

遇到复合需求时，保留一句简短用户原话或可定位的权威来源，并拆成可观察的 `ADD`、`REMOVE`、`MOVE`、`RETAIN`、`REPLACE` 原子。每个原子都用最终产品状态描述，并映射到一个验收 ID 或明确的不做原因。映射直接写在现有 Authoritative inputs 与 Acceptance criteria 中，不新增需求文档。

“不显示”“没有”“不能”“没改”等否定表达既可能是在描述当前问题，也可能是在表达目标结果。应根据需求、原型、当前界面、测试和后续上下文判断方向；如果证据无法判断且两种解释会产生不同结果，只问一个简短的二选一结果问题，不得静默选择。

“以 CTO 视角”等角色提示可以提供思考角度，但不能替代项目证据、验收条件或人工权限。发生上下文压缩或后续写任务时，即使同时使用调试、审查 Skill，也必须重新执行 RigorBreeze 状态与认领检查。

批准前确认：

- 测试观察哪个公共接口或业务边界；
- 哪个独立预期定义成功；
- 允许修改哪些生产路径；
- 验收依据哪个需求或设计版本。

随后执行一次语义自检。拒绝未解决占位符和内部矛盾，拆分过大的结果，并把事实源、新鲜度、兜底和失败行为说明到不存在双重解释。UI 修改应按适用情况覆盖四类验收：必须存在、必须不存在、位置/顺序、必须保留的行为。批准前展示一份精简的最终状态清单，并确认每个可观察原子都有归属。能从仓库恢复的事实直接修正；只有不同答案会显著改变结果时才询问开发者。

Skill 会先调用自身 bundled runner 并检查 `installation` 投影。任务合同不存在、批准无效、当前窗口未认领 worktree，或执行器/配置/基线不可用时，不得开始修改产品代码。活动任务会冻结项目执行器升级；应使用 bundled runner 完成或安全放弃任务，再由 `init` 更新受管文件。

### 观察 RED

L1、L2 和 Emergency 必须在修改生产实现前观察真实失败：

- 把失败绑定到验收 ID；
- 通过公共接缝执行相关测试；
- 记录命令、退出码、预期失败、基线 SHA 和测试摘要；
- 拒绝导入错误、工具缺失、无关历史失败或已经通过的测试；
- 不允许通过调用或复制被测实现来计算预期结果。

L1 和 L2 的 RED 至少引用一个真实测试文件；Emergency 可以改用确定性的事故复现。源码字符串搜索可以证明导出项或配置键等静态合同，但不能单独证明用户行为或业务逻辑。

处理缺陷时，先建立确定、快速、可由 Agent 运行的复现。排列可证伪假设，只增加能够区分假设的观测，删除临时探针，保留回归测试。同一缺陷连续三个假设失败后停止叠加补丁，保存尝试证据，重新审视模块边界、共享状态、所有权和错误架构假设，再决定第四次修改。

### 按 tracer bullet 实现

重复执行：

```text
一个失败行为
→ 最小 GREEN 实现
→ 保持 GREEN 的重构
→ affected profile
→ 下一个行为
```

不要先批量写完全部测试再批量实现，也不要加入顺手重构或推测性抽象。

### 保持精简，但不破坏生产合同

创建 helper、子系统、配置层或新依赖前，先检查仓库现有的标准库、框架和当前依赖。优先使用能满足已批准合同的最小、成熟且仍在维护的现有能力。只有当前验收条件或长期不变量能证明其所有权、供应链成本和维护面积值得承担时，才新增它。

先保留最小可运行的端到端路径，只在独立变更压力、公共合同或安全需求真实存在时提取内聚边界。模块化意味着明确所有权和狭窄职责，不意味着为假想复用制造层级、适配器或扩展点。限时实验可以丢弃，但必须与长期生产路径隔离，不得成为没有记录的“先这样、以后再换”架构。

兼容性是产品合同，不是绝对的“要或不要”。没有声明兼容承诺的代码，只有在调用方、数据和 Git 历史能证明路径已死时才可删除。公开 API、持久化数据、升级路径和生产迁移必须具备明确过渡、验证以及回滚或前向修复策略。只是版本仍小于 1.0，并不能在已有真实用户或数据时授权破坏性修改。

### 验证和关闭

- `affected` 是开发中的快速反馈 profile；
- `full` 是配置的 L1/L2 合并质量 profile；
- `archive` 关闭完成任务，不等于生产发布；
- `archive --outcome abandoned --reason <原因>` 关闭被取消或替代的任务，不宣称完成成功。任务范围内存在未提交代码、自动化仍运行或外部结果未知时会阻断；无关改动只报告。分支、worktree 和提交都会保留；
- `archive --outcome reconciled --reason <原因> --expected-head <sha>` 用于代码已经集成但流程没有关闭的历史任务。它要求精确 HEAD，并通过祖先关系、完整 patch-equivalence，或同基准分支上的明确确认与无产品改动来证明集成；记录原阶段和缺失验证，不伪造 GREEN、验收或发布成功；
- `release` 只在明确请求发布后评估。

正常交付顺序固定为 verify/full → 验收 → 两轮审查 → 复盘 → archive → 受保护 commit/push/merge → reconcile → cleanup。archive 保存只读 `lastClosed` 快照，使产品变化、移动后的合同和对应 evidence 仍可安全提交与交付。同一 worktree 的关闭结果未提交前不能创建新任务；普通归档不会继承 release 权限。

L0 可以在配置验证后归档。L1/L2 必须具备当前 full 验证、适用验收、两轮独立审查和预填复盘确认。

普通提交要求当前配置化 `affected` 或 `full` 结果；targeted 探索不能满足门禁，已有新鲜配置化结果会直接复用而不重跑。archive、merge 和直推集成分支仍属于 full 质量操作。真实 Codex 行为评估是维护者单独执行的发布候选动作，commit、配置化 full 和 CI 都不会触发。

verify、merge、archive 和可选 Git 自动化都检查完整任务变化集：从批准基线到 `HEAD` 的已提交路径，加上当前工作树变化。出现范围漂移时，`status` 优先提示修正范围或拆分任务。merge 或 archive 前，每条当前 RED 链都必须保持测试摘要未变化，并由当前 full 验证对应的 GREEN 闭合。

分两轮执行审查：

1. 规范审查：正确性、简单性、项目约定、安全、可维护性、测试和范围；
2. 规格审查：每个验收 ID、设计状态、接口、数据、权限和禁止边界。

个人开发者可以在不同时间、使用新鲜上下文分别完成两轮审查。

评审意见是需要核验的证据，不是必须服从的权威。先与已批准结果、代码真实使用情况、兼容约束、测试和 YAGNI 对照；无关重构或未使用能力应以证据拒绝，不能借评审扩大范围。

commit、archive 或声称“已修复、已通过、已完成”前，必须引用当前轮次实际运行的准确命令、退出状态和覆盖范围。历史报告、局部检查或其他 Agent 的成功声明不能替代新鲜证据。

## 4. 质量策略

`rigorbreeze.toml` 只声明项目真实使用的检查。所选 profile 中的每个检查都必须完成配置，生成要求的报告，并在 enforced 模式通过。profile 之外的能力不需要填写 `N/A`。

常见可选检查 ID：

- format、lint、typecheck；
- unit、integration、E2E、contract；
- secret、dependency、license、SBOM；
- migration、build、Playwright、acceptance。

一次性探索和调试命令可以直接执行，但不能满足工作流门禁。配置 profile 是本地和 CI 共享的合同。

在单次 profile 调用内，argv、解析后 cwd、有效环境和 timeout 完全一致的检查共享一次进程结果。每个检查仍独立校验自己的报告和制品，并以 `reusedFromCheckId` 说明复用来源；不会跨 profile、Session 或项目变化缓存结果。

L2 的 `full` 根据风险和实际变化推导不可省略的最低集合：secret、build、至少一项静态质量检查和至少一项行为检查。修改依赖清单时额外要求 dependency、license、SBOM 检查及非空报告；修改迁移时要求配置的 migration 适配器与报告。L0/L1 仍由项目声明，不继承与任务无关的企业工具。

始终保留以下边界：

- 暂存文件不能超出批准范围；
- 工作流策略和执行器文件与产品文件一样，必须显式进入 Allowed Scope；
- 秘密和敏感文件不得进入提交或证据；
- 依赖与迁移变更必须被识别并明确审查；
- 源码、测试、依赖、配置、迁移或任务变化后，旧证明失效；
- 发布适用时，测试、UAT、制品和发布必须引用同一 Git SHA 与不可变制品摘要。

合成脱敏 fixture 可以在秘密形状所在的同一物理行标记 `rigorbreeze: synthetic-secret`，但文件必须位于配置测试路径中。该豁免只作用于这一行的内置内容启发式：秘密路径、同文件其他行和项目配置的 secret 适配器仍正常阻断，输出也只报告文件与行号。

本地 advisory 模式帮助快速迭代。远程 Required Checks 和受保护环境才是不可绕过的合并与发布权威。

## 5. 真实验收与发布

根据实际变化的能力进行验收：

- UI：真实运行、关键加载/空/错误/无权限状态、截图、可访问性和适用的 Playwright 证据；
- 小程序：正式构建、开发者工具自动化、真实 AppID/HTTPS 环境和真机证据；
- 权限：角色、租户、归属、数据范围和禁止访问；
- 迁移：克隆数据演练、前后断言、备份恢复或前向修复证明；
- 外部集成：优先使用脱敏真实响应或厂商沙箱 fixture；覆盖启用、关闭、依赖不可用及失败行为；按适用性验证序列化格式、文本 JSON、URL 编码次数、数据库方言语义、订单创建等业务前置条件。Mock 或临时凭证只能证明局部合同/构建，不能替代真实验收。

视觉基线必须由人批准，不能只为消除失败而更新截图。

只有明确生产发布才要求：

- 测试、UAT 和部署使用同一不可变制品与 Git SHA；
- 功能开关和分阶段放量范围；
- 观察窗口、SLI/SLO 和告警负责人；
- 可执行回滚或前向修复命令；
- 适用的业务指标和用户反馈证据。

L2 发布还要求绑定当前 Git SHA 和制品摘要的机器 JSON `operation-plan`。它按顺序列出备份、配置冻结、迁移、部署、验收、流量切换和观察阶段；每一步都有成功条件，并包含停止条件、安全恢复点和回滚限制。任何远程写操作前都要展示完整计划，并指出本次只执行哪一步。

任何外部 Git、部署、开发者工具或平台写操作前，必须读取外部系统本身，不能只相信旧计划或聊天摘要。先展示观察到的当前状态、已经完成的步骤、不可变标识、唯一剩余动作和停止条件。不能仅因为旧清单仍列着某一步，就重复构建、上传、迁移、部署或提升版本。

执行后记录 `operation-result`。`paused` 或 `failed` 必须写明已完成步骤、当前安全状态和唯一恢复入口。例如迁移成功、候选实例失败但旧实例仍健康时，应从候选部署继续，而不是重复迁移或整套重跑。这些记录只是操作快照，不会扩张成常驻部署调度器。

AI 可以整理证据，但不能自行给出安全例外、法律判断或生产批准。

临时或合成凭证只能证明项目可以构建，不能证明真实环境、授权部署或满足验收与发布证据。

## 6. 人工判断

机器事实保存在 `spec/evidence/<TASK-ID>.json`：批准基线、RED、检查、耗时、失效、报告、文件摘要、Git SHA、制品和验收。

L1/L2/Emergency 归档前，Codex 展示预填的 `retro --json` 摘要。只询问开发者：

1. 如有返工，主要原因是什么；
2. 是否存在不合理阻断、绕过或 `nextAction`；
3. 流程是 helped、neutral 还是 hurt。

确认绑定当前任务和项目指纹。L0 不强制复盘。执行器漂移、旧任务占位、运行资源冲突、缺少操作计划和门禁失败会自动去重记录为实践事件。用户出现“我的意思是”“你漏了”“理解反了”等纠正时，在现有复盘异常中记录 `requirement-interpretation-correction`，并归类为 `missing-atom`、`reversed-intent`、`wrong-source` 或 `scope-change`。正确阻断只进入统计；只有人工确认的误阻断、不合理下一动作、绕过、工作流导致的返工或 `hurt` 才成为演进候选。不创建第二份实践日志，也不保存聊天全文。

普通候选第一次出现先观察，第二次同类问题再审查。若流程错误放过秘密、越权、破坏性迁移、过期证据、未授权外部动作或错误发布，则立即审查。

## 7. 并行交付

并行写入遵循固定边界：

```text
一个项目入口
→ 每个写任务一个 rigorbreeze/<task-id> 分支和隔离 worktree
→ 每个 worktree 一个活动任务
→ Git common directory 中一份可重建注册表
```

每个 Codex 窗口保持稳定的 `RIGORBREEZE_SESSION_ID`。第二个存活 Session 不能认领同一 worktree。`status --all --json` 是所有窗口和可选外部编排器的只读接口。

所有 worktree 状态都保存在 Git 私有目录。`status --json` 从真正基准分支投影工作流基线，区分 missing、partial、modified、current 和 blocked。一次性 baseline commit 只能在该分支、精确 expected HEAD、无活动任务且没有混入产品改动时执行。

独立任务不创建 DAG。真实顺序通过每个任务唯一的 `Depends-On` 保存，执行器推导 ready、环、缺失依赖和拓扑顺序。没有依赖关系的活动任务不得拥有重叠 Allowed Scope；应拆分、排序或建立共享 Integration 任务。

`Depends-On` 只表示同仓库任务。跨仓库交付时，每个仓库各自保存合同和证据，并在 Authoritative inputs 中关联对方任务与共享 API/数据契约；提供方接口完成集成和验证前，消费方不得完成真实验收。

自动化等级逐级包含但必须显式启用：

| 等级 | 允许动作 | 必要边界 |
|---|---|---|
| manual | 默认只验证；可执行一次明确要求的 commit/push | 无无人值守写权限；单次授权不保留 |
| commit | 提交批准的任务文件 | 当前门禁，无无关修改 |
| push | 推送 `rigorbreeze/<task-id>` | 不推受保护分支，不 force push |
| merge | 请求平台 auto-merge | 当前 Required Checks 和基线 |
| release | 调用配置的发布适配器 | 同一 SHA/制品和完整治理 |

平台结果保存在 Git 私有自动化日志中，避免外部动作污染 tracked evidence。`status --all --json` 会投影可清理、需保留和未登记 worktree，以及默认保留的任务分支，并给出干净状态、集成状态、expected HEAD 和确认要求。集成必须由祖先关系或完整补丁等价证明。对于已登记任务，只有至少一个产品补丁在 `git cherry` 中为负向/已等价，且所有剩余正向提交只包含该任务白名单工作流元数据时，才可忽略这些元数据提交；任何混合或未匹配产品路径都保持活动。未登记证明继续保持原有保守策略。受管清理要求完整创建来源；未登记清理还要求一次性明确绝对路径、base、expected HEAD、干净且无活动状态，并证明完整集成。本地分支始终保留。

用户明确要求交付当前任务时，Codex 可以执行 `automate commit --once`，或执行 `automate push --once --remote <名称> --branch <当前分支> --expected-head <SHA>`，且不修改 `rigorbreeze.toml`。push 不会隐式提交，会在写入前 fetch，只允许 fast-forward，不会 rebase 或 force push，并在完成后核对远端 SHA。直推集成分支还必须具备当前 full 验证、结构化验收和审查。单次授权不适用于 merge、release、生产迁移或回滚。

## 8. 复杂度边界

- 不为每个证据类别创建一份人工文档；
- 不让每个项目声明所有标准检查；
- 不重复 evidence、attestation 或实践日志；
- 不把普通归档绑定到生产制品和灰度字段；
- 不为简单任务创建 worktree、DAG、代码图谱、向量索引或 Agent 控制台；
- automation 为 `manual` 时不执行未经用户明确要求的 Git 或生产动作；单次 commit/push 是唯一例外；
- 不把流程指标本身当成交付目标；
- 不为一次问题建立永久抽象。

只有真实使用证明必要时才修改共享 Skill。能通过项目配置、可选适配器或更好提示解决的问题，不应增加所有用户的固定成本。
